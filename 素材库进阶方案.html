DESIGN NOTE v2.3 · 2026-11-07 · P0 / P1 已落地，P2 起仍为方案

大规模素材库进阶方案

核心结论：当素材从「几十条」变成「几百上千条 YouTube 视频」，瓶颈不再是模型够不够聪明，而是导入吞吐、检索是否偏斜、标注是否可维护。

适用前提：单机单盘 500G、原片长期保留、短期 50–100 条视频并向更大规模演进；目标仍是「我或 AI 定主题 → 自主合成视频」。硬约束：不改动现有 GUI，AI 能力放在新增的独立页面；视频不上传 AI、Key 本机加密、只监听 127.0.0.1。

0 · 规模假设改变了什么

按你确认的规模分两档算（每条视频约 10 分钟、400 行英文字幕）：

50–100 条短期实际规模：2–4 万行字幕，约 2000–8000 条例句
约 700 次短期全量 AI 分析调用数（60 行/批）；串行约 1–3 小时，尚可接受
500G 单盘长期上限：原片长期保留，按 100–300MB/条约可存 1000–3000 条，需给成片与中间文件留余量
规模修正：短期 50–100 条下，吞吐压力明显小于 v1 假设的 500 条，P0 的紧迫度从「立刻会崩」降为「现在做最省事」。但检索偏斜依旧存在：LIMIT 400 在 2000–8000 条例句里只覆盖 5–20%，且按标题排序，仍会系统性偏向前几个视频。这一条不因规模缩小而消失。

由此浮出三个和「小规模」完全不同的问题：

  1. 检索偏斜（最致命）：library_pick() 用 ORDER BY v.title, s.start, s.id LIMIT 400 取候选。即使短期只有 2000 条例句，AI 也只看到按标题排序最靠前的 400 条。「做一期 I am going to 的」会系统性漏掉绝大多数素材，不是模型问题，是召回问题。
  2. 无用功：全量 AI 分类意味着从未被使用的素材也等了时间；规则一改（比如句型归一方式变了），全库标注跟着漂移，重跑代价随规模线性增长。
  3. 质量不可追溯：视频多到无法逐条试听时，「切点会不会缺头尾字」必须能在合成前被自动筛掉，而不能只靠事后听。现在没有可筛选的元信息。
一个诚实修正：按当前 DeepSeek 价格，短期 700 次、长期 3500 次调用的成本都在十几元量级，省钱不是主要动机。真正要优化的是吞吐时间、无效标注、以及标注漂移后的可追溯性。任何以「省 API 费用」为卖点的方案都抓错了重点。

界面边界：新增，不替换

现有三个入口全部保留、不做删改：web/index.html（制作）、web/library.html（素材库）、web/publish.js/css（发布准备）。新增 web/studio.html 作为第四个入口，只做「说需求 → 看计划 → 一键执行 → 看成片」。它复用同一份 app.py 后端、同一个素材库和同一个 auto_produce()，不复制数据、不另建一套选段逻辑。

Android 端需把新静态页复制进应用私有目录并加入口，按 android/AGENTS.md 的既有做法处理，不改动现有 WebView 加载逻辑。桌面与手机共用这套新页面，不写第二套实现。

这一点也回答了「对话框会不会让原页面多余」：不会。新页面负责意图与执行，老页面继续负责看、听、微调和发布，职责不重叠。

关于「AI 做语音转写」——它到底是什么

不是把音频发给 DeepSeek。语音转写（ASR）是一个在本机运行的语音识别模型（whisper.cpp / faster-whisper 一类），音频不出本机、不上传、不耗 API Token；代价是几百 MB 到几 GB 的模型文件、CPU/GPU 占用，一条 10 分钟视频通常要转写数分钟，Windows 便携包和 Android APK 体积都会明显变大，手机端尤其吃力。

它唯一能解决的是「字幕文字和画面里说的不一样」——YouTube en 自动轨会改写、丢词，历史实测与 en-orig 相似度仅 66.8%。这类错误靠音频包络、切点吸附、选轨优先级都修不了。

建议短期不做。理由有三：你已确认当前痛点是切点时间不准（时间轴问题），不是文字错；短期 50–100 条下，选 en-orig 轨加人工抽检足够；引入本地 ASR 会同时冲击打包体积、Android 可行性与长任务耗时。若将来确实需要，建议只做 Windows 端可选的单句校对工具，不进主流程、不进 Android、不自动改写字幕。

软引导的正确实现：计划里的每个维度（句型、话题、场景、语法点、来源视频、时长…）都是一条带权重的偏好，参与召回打分，不是 WHERE 硬条件。AI 精排可以保留少量「相关但不同句型」的表达做对照，这正是软引导相对硬筛的价值。维度定义放在可扩展配置里，加新维度不需要改执行链路。

1 · 五个结构性判断

判断一：导入只做「事实层」，AI 标注必须惰性化

视频与字幕导入应当是本地、免费、秒级、可并行的：字幕轨来源、词级时间戳、完整句边界、语音起止、音轨有无、时长画幅、可独立使用性，全部是确定性计算，不需要模型。AI 只在用户主动分析或某批素材首次被检索召回时才触发，且只作用于召回的小集合。

项目约定已要求「AI 分段仅在用户主动点击时发送字幕」「素材库分析只补未完成批次」，这个方向不是新约束，是把既有约定贯彻到大规模场景。

判断二：先结构化召回，再 AI 精排，不能反过来

现状是「把 400 条例句一次塞给 AI 让它挑」。正确形态是两段式：SQL / 全文索引按句型、话题、关键词、轨质量召回 Top-N（如 200 条）→ AI 只在这 200 条里排序、判离题、给建议顺序。library_search() 已有 pattern 参数与 matches_pattern，只是没接进 library_pick() / auto_produce()。

这一步同时解决「按句型做一期」以及后续按话题、场景等其他维度做一期：维度作为加权偏好参与召回，AI 精排再综合判断，既不会只靠提示词祈祷，也不会把相关但不同句型的对照表达全部排除（软引导）。

判断三：越想全自动，越需要结构化事实，而不是更全的分类

值得结构化存储的，只有同时满足「AI 从原始文字推不出来」+「错了会毁掉成片」的信息。典型是字幕轨来源和切点可信度。反过来，情绪、场景、CEFR 难度、教学法分类这类推测性标签，AI 看文字八九不离十，猜错还会污染筛选——不该建。

判断四：稳定主键不能是文件路径

现在 register_project_source() 用 sha256(视频绝对路径) 作素材 id。批量下载后会整理文件夹、换盘、归档，路径一变就是新素材，例句与出处全部断链。大规模下应改用 YouTube video id 作稳定主键，路径降级为「可重定位的属性」。

判断五：质量门禁比「更准的吸附」更重要

refine_clip_edges() 已经会在本地把切点吸到语音边缘，但它无法告诉你「这次吸附到底可不可信」。把「是否词级时间戳 / 轨来源 / 是否找到语音边缘 / 吸附改动量 / 切点是否落在有声处」记成片段元信息，一键成片就能默认只用低风险片段，把「低概率出错」从愿望变成可量化、可配置的阈值。

2 · 目标架构：五层

L0 · 媒体归档层 P0② 已落地

稳定 media_key（YouTube 视频 ID）、路径变化自动重定位且不丢例句、原片不复制、下载去重与断点；单盘 500G 下不引入多媒体根。对应 download_playlist() / library_import() / sources.media_key。sources.id 保持路径哈希主键不变，避免外键迁移。

↓

L1 · 导入事实层（本地、免费、必做）

字幕轨优先级与来源记录、词级时间戳落盘、完整句边界、语音起止与静音段、音轨/画幅/时长、可独立使用性规则。对应 pick_subtitle_file() / rolling_subtitles() / speech_edges()。

↓

L2 · 索引与召回层（大规模核心）

SQLite FTS5 全文索引（英 + 中）、结构化列（句型 / 语法 / 话题 / 轨质量 / 切点可信度）、两段式召回。对应 library_search() / library_pick()。

↓

L3 · 惰性 AI 标注层

只标最小集：句型、语法、中文释义、话题；每次标注带 model + prompt_version + signature，规则升级可追溯、可增量重跑。对应 library_analyze() / review_segments()。

↓

L4 · 编排与验收层

新增的 AI 工作室页面：自然语言 → 可编辑执行计划 → auto_produce() 执行；现有页面原样保留，继续承担看 / 听 / 微调与发布。不可逆动作显式确认，感知类动作保留人工入口。

顺序不可颠倒。 L0–L2 是地基；没有稳定召回，L3 的标注再细也挑不到，L4 的对话框只会变成一个漂亮但经常猜错的壳。

5 · 每层的关键取舍

L1 事实层：只算「事实」，不算「画像」

导入时对每条字幕产出一份本地元数据：轨来源、是否词级时间戳、句边界类型（标点 / 停顿 / AI 兜底）、语音起止、静音段、句子长度、是否含方括号标注、是否可独立使用。全部规则判定，零 API 调用。其中词级时间戳最该先做——rolling_subtitles() 已经算出了 word_ends，只是生成 rows 时丢掉；把它留下等于免费获得更准的片段边界。

明确不做：导入时全量 AI 分类、情绪/场景/难度评分、自动生成内容摘要、语音转写、逐帧画面理解。这些要么推测性强，要么违反项目约束，要么在大规模下成本随时间线性爆炸。

L2 召回：两段式，且索引要能增量

用 FTS5 建英文 + 中文全文索引，结构化列单独存（句型、语法、话题、轨质量、切点可信度、时长）。library_pick 改为：先按执行计划里的加权偏好做多路召回并合并打分（句型 / 话题 / 关键词 / 质量阈值各占权重，不设硬过滤），取 Top-N，再让 AI 在召回集里排序与复查。召回结果按视频 id 做配额，避免一期 8 段全来自同一个视频。索引随导入增量更新，不需要全库重建。

L3 标注：最小集 + 版本化

每条标注记录 model / prompt_version / signature。规则升级时只重跑受影响或 pattern_version=0 的行（现有表已有这个字段），不做全库重算。标注是惰性的：素材首次被召回或用户主动点「分析字幕」时才生成，未被使用的素材保持「已导入、未标注」状态。

L4 编排：计划先于执行

自然语言解析的产物不是动作，是一份可编辑、可落盘的执行计划：来源（单视频 / 素材库）、一组带权重的软偏好（句型、话题、场景、语法点…可增可减）、段数、长度、模板、画幅、字幕版本、是否生成封面文案。用户确认后交给现有 auto_produce()。计划落盘是为了可复现——同一句话两次跑出不同选段时，能复盘到底是哪个参数变了。

维度用「权重表」表达而不是写死字段：今天按 I am going to 做一期，明天按「机场问路」「过去完成时」「某个 UP 主」做一期，加的只是新维度与权重，召回、精排、合成链路一行不改。这也是「软引导」和「硬筛」在工程上的真正差别。

6 · 风险与项目约束

风险说明与对策
字幕文字本身错YouTube en 自动轨会改写 / 丢词（历史实测与 en-orig 相似度仅 66.8%）。选轨优先级已缓解，但在「不引入语音转写」的既定约束下无法自动消除。方案只能标记轨质量并降低高风险片段权重，不能承诺零错误。
YouTube 风控批量下载会遇到登录验证 / Cookie 过期 / 出口 IP 标记。已有 Cookie 显式导入、失败列表与「仅重试失败项」；大规模下应加限速与失败退避，不能靠提高并发硬冲。
存储与路径原片是最大开销。坚持「原片归档 + 项目引用，不复制」；代价是移动或删除原片后引用项目失效，需提供批量重定位，而不是静默重下。
兼容性新增表与字段不得改变旧 project.json 和 sources 的既有语义；迁移脚本必须可逆、不触碰用户素材与已生成成片。
安全边界视频 / 音频不发 AI，AI 只收字幕文字；Key 本机加密；只绑 127.0.0.1 + 随机令牌；不关 TLS 校验；Cookie 只来自用户显式导入且不入库、不进发行包。

7 · 验收标准（可量化，别用「感觉变好了」）

  • 导入吞吐：批量导入 100 条视频完成事实层提取，零 AI 调用，耗时可测；重复导入不产生重复记录。
  • 召回覆盖：库内 2000 条例句时，「做一期 I am going to」能召回覆盖 ≥5 个不同视频的候选，而不是集中在标题最靠前的两三个；且允许保留少量对照表达（软引导）。
  • 切点质量：抽样人工试听 N 段，统计「缺头尾字 / 多出静音」发生率；质量门禁开启后该比例应明显下降，且可给出被拦截片段数。
  • 可复现：同一份执行计划跑两次，选段集合一致（AI 精排结果允许在计划里固定随机性或缓存）。
  • 成本可见：执行前显示本次预计 AI 调用次数，执行后显示实际 Token；与实际账单可对照。
